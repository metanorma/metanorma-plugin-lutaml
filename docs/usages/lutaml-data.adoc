== Usage with typed data files by lutaml_data

=== General

The `lutaml_data` block command loads data that is defined with LutaML models
and makes it available to a Liquid template in the block.

The data consists of two parts:

* the *data definitions*: LutaML models in a `.lml` file, or an XML Schema in a `.xsd` file; and
* the *data instances*: values of those models, written in `.lml`, `.yaml`,
  `.yml`, `.json` or `.xml` (with an XSD definition).

=== Defining a block

Data definitions and data instances in separate files:

[source,asciidoc]
------
[lutaml_data,{definition_file},{instance_file},{context_name},options={...}]
----
...Liquid template...
----
------

Data definitions and data instances in the same `.lml` file:

[source,asciidoc]
------
[lutaml_data,{definition_file},{context_name},options={...}]
----
...Liquid template...
----
------

`definition_file`:: (required) Path to the `.lml` file that holds the LutaML
models, or the `.xsd` file that defines XML instances. Relative paths are resolved from the directory of the Metanorma
document. A lone `.lml` file must also contain the instances; an XSD
definition always requires a separate XML instance file.

`instance_file`:: (optional) Path to the file that holds the data instances,
with extension `.lml`, `.yaml`, `.yml`, `.json` or `.xml`. The `.lml` instance file
usually starts with `require "<definition_file>"`.

`context_name`:: (optional) The name under which the data is exposed to the
Liquid template. Defaults to `lutaml_data`.

`options`:: (optional) Rendering options, given either as a JSON object
(`options={"include_path":"templates"}`) or as inline `key=value` pairs
(`include_path=templates`). The supported option is `include_path`, a
comma-separated list of directories searched by the Liquid `include` tag.

NOTE: A segment is taken as the instance file when its extension is one of
`.lml`, `.yaml`, `.yml`, `.json` or `.xml`; any other segment is taken as the context
name.

=== Data in the Liquid context

The data is exposed under `context_name`, then the name of the instance.

* For `.lml` instances, the key is the instance name (`instance S158Checks { ... }`
  is `S158Checks`).
* For `.yaml` and `.json` instances, the key is the model name given by the
  required `type` entry (`type: Widgets` is `Widgets`). A file may hold one
  object or a list of objects.

Attributes are read by name (`check.dev_id`), collections are iterated with
`for`, and enum values expose the attributes defined in the model
(`check.classification.description`).

=== Example

Data definitions, `s102_models.lml`:

[source]
----
models IhoS102Check {
  enum CheckClassification {
    critical_error {
      description "Critical Error"
    }
    warning {
      description "Warning"
    }
  }

  class ValidationChecks {
    attribute checks {
      type ValidationCheck
      cardinality 0..n
    }
  }

  class ValidationCheck {
    attribute dev_id {
      type String
      cardinality 1
    }

    attribute classification {
      type CheckClassification
      cardinality 1
    }

    attribute check_message {
      type String
      cardinality 1
    }
  }
}
----

Data instances, `s102_checks.lml`:

[source]
----
// s102_checks.lml
require "s102_models.lml"
instance S158Checks {
  type ValidationChecks

  checks = [
    instance IhoS102Check::ValidationCheck {
      dev_id = "S102_Dev1001"
      classification = CheckClassification::critical_error
      check_message = "No feature information group"
    },

    instance IhoS102Check::ValidationCheck {
      dev_id = "S102_Dev1002"
      classification = CheckClassification::warning
      check_message = "Mandatory metadata attribute missing"
    }
  ]
}
----

NOTE: In `.lml` files, comments start with `//`. A `#` comment is rejected by
the instance parser.

The Metanorma document:

[source,asciidoc]
------
[lutaml_data,s102_models.lml,s102_checks.lml,lml]
----
{% for check in lml.S158Checks.checks %}
=== S-102 Validation Check `{{ check.dev_id }}`

classification: {{ check.classification.description }}

check message: {{ check.check_message }}

{% endfor %}
----
------

renders as:

[source,asciidoc]
----
=== S-102 Validation Check `S102_Dev1001`

classification: Critical Error

check message: No feature information group

=== S-102 Validation Check `S102_Dev1002`

classification: Warning

check message: Mandatory metadata attribute missing
----

=== Instances in YAML or JSON

The same data can be given as YAML (`s102_checks.yaml`):

[source,yaml]
----
type: ValidationChecks
checks:
  - dev_id: S102_Dev1001
    check_message: No feature information group
----

NOTE: Enum-typed attributes (such as `classification` above) cannot currently
be set from YAML or JSON instances; loading fails. Use `.lml` instances for
data that has enum values.

The key in the template is the type name:

[source,asciidoc]
------
[lutaml_data,s102_models.lml,s102_checks.yaml,lml]
----
{% for check in lml.ValidationChecks.checks %}
{{ check.dev_id }}
{% endfor %}
----
------

=== Instances in the definition file

If the instances are in the definition file, omit the instance file:

[source,asciidoc]
------
[lutaml_data,widgets.lml,store]
----
{% for widget in store.AllWidgets.widgets %}
{{ widget.id }}: {{ widget.name }}
{% endfor %}
----
------

=== Options

Directories for Liquid `include` can be set with `options`:

[source,asciidoc]
------
[lutaml_data,widgets.lml,store,options={"include_path":"templates"}]
----
{% include 'heading' %}
----
------

=== Data from a provider

A Ruby gem can expose data to documents as a provider. The block names the
provider and one of its queries instead of a definition file, and passes the
query's keyword arguments under `arguments` in `options`:

[source,asciidoc]
------
[lutaml_data,provider:ituob.edition,edition,options={"arguments":{"register":"e212-mnc","as_of":1170}}]
----
{{ edition.register }} as of issue {{ edition.as_of_issue }}
{% for row in edition.items %}
{{ row.mnc }} {{ row.network }}
{% endfor %}
----
------

The query's result reaches Liquid unconverted: lutaml-model objects answer
`to_liquid` themselves, so the template reads the provider's typed
attributes, in the order the provider returns them. The plugin never turns
them into hashes.

==== Writing a provider

A provider gem ships
`lib/metanorma/plugin/lutaml/data_providers/<name>.rb`, which registers a
factory:

[source,ruby]
----
Metanorma::Plugin::Lutaml::DataProviders.register("ituob") do
  Ituob::Provider.new
end
----

The plugin requires that file the first time a document names the provider,
so the provider gem only has to be in the document's bundle. Provider names
are lowercase letters, digits and underscores.

The provider object lists the queries a document may call:

[source,ruby]
----
def lutaml_data_queries
  %i[edition history]
end
----

Any other method, public or not, cannot be called from a document. A query
takes keyword arguments (JSON keys become keywords, JSON numbers stay
numbers) and returns lutaml-model objects or arrays of them. An unknown
provider, an undeclared query or a wrong argument fails the block with an
error.

=== XML instances defined by XSD

An XML instance requires a separate XSD definition. Supply the schema first,
then the XML file, followed by the optional context name:

[source,asciidoc]
------
[lutaml_data,catalogue.xsd,catalogue.xml,fc]
----
{{ fc.Catalog.name }}
----
------

Here `Catalog` is the XML root element's local name and `name` must be an
attribute actually generated from that schema. The context defaults to
`lutaml_data`, giving `lutaml_data.Catalog`. Values remain typed model objects;
Liquid reads their generated attribute names and iterates their collections.
Schema element names and generated Ruby attribute names may differ.

Keep local `xs:import` and `xs:include` dependencies beside the schema, preserving
the relative paths in `schemaLocation`. The `location` option supplies a base
path for compiler import resolution. XML prefixes may differ from the schema's
prefixes; the namespace URI identifies the root declaration.

The loader validates XML against the XSD before compiling and hydrating the
model. A missing file, malformed XML, wrong root,
invalid schema value or unsupported compiler construct fails the block with
both input paths in the diagnostic. XSD validation enforces the schema
constraints, including enumeration values and occurrence limits. Successful
schema validation alone does not establish that the compiler can load every
imported type.

==== S-411 2014 acceptance corpus

The repository contains the original `S411FC.xml`, `S100FC.xsd` and its three
imported schemas under `spec/fixtures/lutaml/xml_data/s100/`. The manifest records
publication URLs and byte checksums. The XML catalogue declares version 1.0.0
(2014-02-13), distributed with S-411 Edition 1.1.0 (June 2014).

The standalone `catalogue.adoc` loads the schema/XML pair and includes the
plain Liquid template beside it:

[source,asciidoc]
------
[lutaml_data,S100FC.xsd,S411FC.xml,fc]
----
{% include 'catalogue' %}
----
------

The template emits one clause per feature using
`fc.Catalog.feature_types.feature_type`. Optional attribute containers are
collections, including containers whose maximum occurrence is one:

[source,liquid]
----
{% for group in fc.Catalog.simple_attributes %}
{% for attribute in group.simple_attribute %}
{{ attribute.name }}
{% for value in attribute.listed_value %}
{{ value.code }}: {{ value.label }} — {{ value.definition }}
{% endfor %}
{% endfor %}
{% endfor %}
----

Feature `attribute_binding` entries refer to attribute definitions through
`binding.attribute.ref`; match that reference to an attribute's `code`.
Complex attributes contain `sub_attribute_binding` references which are resolved
in the same way. The complete `catalogue.liquid` demonstrates both traversals.
XSD integer values use their numeric representation: listed-value code `01`
renders as `1`, while its string label remains `01`.

This example is verified against an *unreleased lutaml-model compiler
candidate based on 0.8.176* (commit
`c21b2f8d4e91efe6937b6c4637a5102249b8a7e5`) which fixes the built-in
`xs:ID` and `xs:IDREF` mappings. Released 0.8.176 cannot load this schema's generated
`ItemIdentifier` class. No released minimum version containing the fix is
claimed here. Select the patched dependency in your bundle; while testing an
unreleased checkout, the equivalent explicit command from the plugin repository
is:

[source,shell]
----
RUBYLIB=/path/to/patched-lutaml-model/lib bundle exec ruby -Ilib \
  spec/fixtures/lutaml/xml_data/s100/render.rb > /tmp/s411-catalogue.xml
----

The integration CI writes a `Gemfile.devel` selecting that exact compiler commit
before Bundler runs. This tests the unreleased candidate without changing the
gem's released dependency floor. Remove the CI pin when a containing release is
selected by the owner.

`render.rb` registers the data preprocessor and converts the standalone document
with the Metanorma `standoc` backend. The schema closure, XML, document and
template remain separate source files; no pre-generated clause text is used.
The acceptance spec checks all 28 feature identities, 57 attribute definitions,
406 listed values and reference resolution independently from source XML, and
requires positive clause content plus changed-input and repeated-load checks:

[source,shell]
----
RUBYLIB=/path/to/patched-lutaml-model/lib bundle exec rspec \
  spec/metanorma/plugin/lutaml/xml_data_s100_spec.rb
----
